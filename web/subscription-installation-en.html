Subscription service installation

The subscription service renders the connection page and supplies VPN client configurations. On the panel server it can use the local database; on a separate server it requests data from the panel API over HTTPS.

Language and short links

Customer links use https://sub.example.com/ID. Existing /s/ID links continue to work without redirects or re-importing subscriptions. QR codes, the bot, customer portal and Mini App use the short URL.

The connection page supports Russian and English. The RU / EN button at the top changes the language and remembers it on this domain. The first visit follows the browser language; use ?lang=en or ?lang=ru to set a specific link’s language. Page language does not change the configuration imported by VPN apps. Plan names, location names and custom owner messages remain as entered by the owner.

For separate servers, update sn-sub on the subscription server to v0.1.9 or later before updating the panel, which will start generating short links. Existing links keep working after the update. Standalone service update instructions are below.

1. Configure the panel

Open Settings → Subscription service. Save the panel URL and a dedicated subscription URL. The subscription domain must resolve to the server that hosts this service. For a separate server, issue and privately save the project service key.

2. On the panel server

When “On this server” is selected, the panel installer installs sn-sub alongside the API. The subscription service listens on 127.0.0.1:8081; Caddy handles its HTTPS domain. Check:

systemctl status sn-sub --no-pager
curl -fsS http://127.0.0.1:8081/ready

Do not run the separate-server installer over the panel installation. For an existing Docker Compose deployment, run:

docker compose up -d sub
docker compose exec sub curl -fsS http://127.0.0.1:8081/ready

Inside the shared Compose network, Caddy forwards to sub:8081. A container's 127.0.0.1 refers to that same container.

3. On a separate server

During new panel setup, select “On a separate server”. The subscription domain is saved for customer links; setup does not install local sn-sub or wait for its DNS/HTTPS. Complete subscription setup on the second machine below.

  1. Prepare Debian/Ubuntu with systemd, root SSH access and amd64 or arm64. The server must reach the panel over HTTPS. No PostgreSQL access is required.
  2. In the panel, select Separate server → Installation. Copy the complete generated command.
  3. Run it on the target server. The installer verifies the service key, architecture, download checksum and binary startup, then creates the systemd service and /etc/sn-sub/env with permissions 600.
  4. Verify local readiness, then configure public DNS and HTTPS below.

The matching Linux binary and its .sha256 file must be available on the panel. Release packages include both architectures. A custom build can be selected with SUB_BINARY_URL. An invalid checksum or an HTML response is rejected.

Separate instances use the project's active SUB_SERVICE_TOKEN. After rotating it in the panel, update /etc/sn-sub/env on every separate instance and restart sn-sub. Docker instructions require a real configured SUB_IMAGE; the shell installer does not require Docker.

4. DNS and HTTPS

Point the subscription domain's A record to the selected server. Add AAAA only when IPv6 works there. Allow inbound TCP 80/443 in both the OS and hosting firewall, and keep port 8081 private. Use the existing web server when possible. If the server has none, install Caddy using its official Debian/Ubuntu instructions.

Add this to the existing host Caddy configuration, preserving other sites:

https://sub.example.com {
    encode zstd gzip
    reverse_proxy 127.0.0.1:8081
    header -Server
}

For Caddy in the same Compose network, use reverse_proxy sub:8081. Edit an existing domain block instead of adding a duplicate. Validate and reload:

caddy validate --config /etc/caddy/Caddyfile
systemctl reload caddy
curl -fsS https://sub.example.com/ready

Caddy obtains certificates when DNS and public ports are reachable. Do not disable HTTPS certificate verification between a separate subscription server and the panel.

5. Test a real subscription

Select an active test customer with access to hosts through an internal squad. Open their actual subscription link in the browser. Check status, application selection, connection action and QR code. Import that same URL into a VPN client, update the subscription and test a connection.

/health checks process availability. /ready also checks access to the database or API. Neither verifies a customer's VPN tunnel. A nonexistent subscription returning 404 does not prove a real subscription works.

6. Update

On the panel server, run make update from the installed project directory. For an existing Compose deployment, rebuild with docker compose up -d --build. On a separate subscription server, update this service first, then the panel. Run as root:

curl --proto '=https' --tlsv1.2 -fsSL https://raw.githubusercontent.com/STEALTHNET-APP/STEALTHNET-SOFTWARE/v0.2.2/web/update-sub.sh -o /root/stealthnet-update-sub.sh
case "$(uname -m)" in
  x86_64) SN_SUB_ARCH=amd64 ;;
  aarch64|arm64) SN_SUB_ARCH=arm64 ;;
  *) echo 'Unsupported architecture'; exit 1 ;;
esac
SUB_BINARY_URL="https://github.com/STEALTHNET-APP/STEALTHNET-SOFTWARE/releases/download/v0.2.2/sn-sub-linux-$SN_SUB_ARCH" bash /root/stealthnet-update-sub.sh

The updater preserves the environment file, replaces the binary atomically and checks readiness. It restores the previous binary if startup fails. Re-running the installer is not the update procedure.

Diagnostics

journalctl -u sn-sub -n 50 --no-pager
curl -fsS http://127.0.0.1:8081/ready
journalctl -u caddy -n 50 --no-pager
  • Rejected key: check the panel URL and active service token.
  • 503 readiness: check panel connectivity/key in API mode, or PostgreSQL in database mode.
  • No locations: check the customer's status, internal squads, enabled hosts and node inbounds.
  • Old domain in links: check the subscription URL in settings; allow up to 30 seconds for the settings cache.
  • HTTPS failure: check DNS A/AAAA, TCP 80/443, certificates and web server conflicts.

A separately hosted subscription service still depends on the panel API for new configuration requests. Existing VPN tunnels are handled by their nodes.
