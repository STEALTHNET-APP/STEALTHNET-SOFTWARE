# Платёжные модули

Ядро не знает ни одной платёжной системы в лицо. Оно умеет две вещи: попросить модуль выставить счёт и передать модулю входящее уведомление. Всё остальное — внутреннее дело модуля.

Благодаря этому платёжки добавляются без правок в ядре, а у каждой валюты может быть свой провайдер: рубли принимает одна система, USDT — другая, Telegram Stars — третья.

## Три пути добавить платёжку

Выбирайте самый левый из подходящих — он дешевле в поддержке.

| Путь | Когда подходит | Что нужно |
|---|---|---|
| **Настроить в панели** | у провайдера обычный REST API | ничего, кроме доступа в панель |
| **Свой модуль** | нестандартная подпись, многошаговый протокол, автосписание | Rust и пересборка |
| **Подтверждение вручную** | переводов мало, автоматизировать нечего | ничего |

**Новый модуль нельзя загрузить в работающую панель**: это скомпилированный код, а не скрипт. Поэтому для типовых случаев есть модуль `http` — он настраивается целиком из панели и покрывает большинство платёжных систем.

### Путь 1: настроить в панели

**Продажи → Платёжки и валюты → «Своя платёжка» → Ключи и настройки.**

Модуль подойдёт, если провайдер:

- принимает POST с суммой и возвращает ссылку на оплату в JSON;
- шлёт вебхук со статусом и подписывает его HMAC-SHA256 от тела запроса.

Что заполнить:

| Поле | Пример | Зачем |
|---|---|---|
| Валюты | `RUB, USD` | модуль предлагается только для этих валют |
| URL выставления счёта | `https://api.provider.com/invoice` | куда слать POST |
| Заголовок авторизации | `Authorization: Bearer sk_live_…` | целиком, как требует провайдер |
| Шаблон тела | `{"amount":"{amount}","order_id":"{payment_id}"}` | подстановки ниже |
| Путь к ссылке оплаты | `data.url` | откуда взять ссылку из ответа |
| Секрет вебхука | `whsec_…` | им проверяется подпись |
| Путь к id платежа | `order_id` | по нему находим счёт |
| Путь к статусу | `status` | и значение «оплачено», например `paid` |

Подстановки в шаблоне тела: `{amount}` (сумма в единицах валюты, `599.00`), `{amount_minor}` (в копейках, `59900`), `{currency}`, `{payment_id}`, `{description}`, `{return_url}`.

Адрес для уведомлений провайдеру панель показывает в той же форме:

```
https://ваша-панель/api/pay/webhook/http
```

**`{payment_id}` передавайте обязательно.** Это наш идентификатор счёта; без него уведомление не с чем сопоставить, и оплата не будет засчитана.

**Без секрета вебхука уведомления не принимаются вовсе.** Это не перестраховка: вебхук — открытый адрес, и единственное, что отличает провайдера от постороннего, — подпись.

Чего этот модуль не умеет: схем подписи, отличных от HMAC-SHA256 по телу; протоколов в несколько шагов; автосписания. Нужно что-то из этого — пишите свой модуль.

## Валюта одна на весь сервис

Валюта задаётся в панели: **Продажи → Платёжки и валюты → Валюта системы**. В ней задаются цены тарифов и считаются отчёты. Нескольких валют одновременно нет намеренно: они требуют курса, пересчёта и расходятся в отчётности, а продавцу нужно одно значение.

Единственное исключение — **Telegram Stars**. Они существуют только в собственных единицах и рубли принять не могут, поэтому у периода есть отдельная цена в звёздах:

```
PRO · 30 дней → 5.99 USD   ← валюта системы
PRO · 30 дней → 129 XTR    ← отдельная цена в звёздах, необязательная
```

Цену в любой третьей валюте API отклоняет — иначе появился бы тариф, который в отчётах считается, а купить его нельзя.

## Как выбирается способ оплаты

Когда клиент выбирает период, ядро спрашивает реестр, кто принимает валюту системы, и показывает кнопкой каждый **включённый и настроенный** модуль. Если у периода есть цена в звёздах, рядом появляется кнопка Telegram Stars.

Ненастроенные модули (без ключей) не предлагаются: кнопка, ведущая в ошибку, хуже отсутствующей кнопки.

## Что уже есть

| Модуль | Валюты | Что нужно для работы |
|---|---|---|
| `stars` | XTR | только `BOT_TOKEN` — оплата внутри Telegram |
| `cryptobot` | USD, EUR, RUB | `PAY_CRYPTOBOT_TOKEN` — принимает крипту по курсу фиата |
| `manual` | настраиваются | ничего; администратор подтверждает оплату в панели |

## Путь 2: свой модуль за пять шагов

**1.** Создайте `src/providers/mypay.rs` и реализуйте типаж:

```rust
use async_trait::async_trait;
use crate::{Invoice, InvoiceRequest, PaymentProvider, PaymentStatus, WebhookOutcome};
use sn_core::{Error, Result};

pub struct MyPay {
    token: Option<String>,
    http: reqwest::Client,
}

impl MyPay {
    pub fn from_env() -> Self {
        Self {
            token: std::env::var("PAY_MYPAY_TOKEN").ok().filter(|t| !t.is_empty()),
            http: reqwest::Client::new(),
        }
    }
}

#[async_trait]
impl PaymentProvider for MyPay {
    fn id(&self) -> &'static str { "mypay" }          // menять нельзя: по нему ищутся старые платежи
    fn title(&self) -> &str { "MyPay" }               // это увидит клиент на кнопке
    fn currencies(&self) -> Vec<String> { vec!["RUB".into()] }
    fn is_configured(&self) -> bool { self.token.is_some() }
    fn accepts_http_webhooks(&self) -> bool { true } // только для подписанных HTTP-уведомлений

    async fn create_invoice(&self, req: &InvoiceRequest) -> Result<Invoice> {
        // req.payment_id обязательно передайте провайдеру: по нему
        // вы найдёте платёж, когда придёт уведомление.
        Ok(Invoice {
            pay_url: "https://mypay.example/invoice/123".into(),
            external_id: Some("123".into()),
            expires_in_minutes: 60,
            payload: serde_json::json!({}),
        })
    }

    async fn handle_webhook(
        &self,
        headers: &std::collections::HashMap<String, String>,
        body: &[u8],
    ) -> Result<WebhookOutcome> {
        // ⚠️ ОБЯЗАТЕЛЬНО проверьте подпись и верните Err при несовпадении,
        // иначе любой сможет «оплатить» подписку простым HTTP-запросом.
        if !self.signature_valid(headers, body) {
            return Err(Error::Forbidden);
        }
        // ... разберите тело и верните WebhookOutcome
        todo!()
    }
}
```

**2.** Добавьте модуль в `src/providers/mod.rs`:

```rust
pub mod mypay;
```

**3.** Зарегистрируйте в `Registry::from_env` (`src/registry.rs`) — одна строка:

```rust
Arc::new(crate::providers::mypay::MyPay::from_env()),
```

**4.** Опишите поля настроек — по этому списку панель сама нарисует форму, править её не нужно:

```rust
fn settings_schema(&self) -> Vec<SettingField> {
    vec![
        SettingField::secret("token", "API-токен", "Личный кабинет → Разработчикам"),
        SettingField::text("shop_id", "ID магазина", "Виден в реквизитах").required(true),
    ]
}

/// Куда реестр положит значения из панели.
fn settings(&self) -> Option<Settings> { Some(self.cfg.clone()) }
```

Значения читайте через `self.cfg.get("token")`, а не из окружения напрямую. Тогда ключ меняется в панели и подхватывается **без перезапуска сервисов** — включая бота, у которого свой экземпляр реестра.

`get_or_env("token", "PAY_MYPAY_TOKEN")` дополнительно смотрит в переменную окружения: пригодится, если вы переносите уже работающую установку.

**Секреты помечайте `secret`.** Такое поле не возвращается в панель — только признак «задано». Иначе ключ платёжной системы окажется в браузере, в истории и в логах прокси.

**5.** Перезапустите сервисы. Модуль сам появится в списке; ключи вводятся в панели.

**5.** Укажите провайдеру адрес для уведомлений:

```
https://ваш-домен/api/pay/webhook/mypay
```

Последний сегмент — ваш `id()`.

## Автосписание (необязательно)

Если ваша платёжка умеет списывать без участия клиента — реализуйте ещё два метода, и автопродление заработает само:

```rust
fn supports_recurring(&self) -> bool { true }

async fn charge_saved(&self, req: &InvoiceRequest, provider_token: &str)
    -> Result<WebhookOutcome> { ... }
```

`provider_token` — то, что модуль сам сохранил при первой оплате в `payment_methods`. **Карточные данные система не хранит и не передаёт** — только токен провайдера.

Модули без этой способности (Telegram Stars, криптоплатежи) ничего не теряют: система за сутки до окончания пришлёт клиенту напоминание со ссылкой на продление. Это осознанный режим, а не заглушка — заставить криптоплатёж списаться без клиента невозможно в принципе.

## Чего делать нельзя

**Не пропускайте проверку подписи.** Вебхук — открытый endpoint без авторизации, так и задумано: авторизацию обеспечивает подпись. Если её не проверять, подписку можно получить бесплатно, отправив один запрос.

**Не сравнивайте подписи обычным `==`.** Сравнение строк выходит раньше на первом различии, и по времени ответа подпись можно подобрать. Пример сравнения за постоянное время — в `providers/cryptobot.rs`.

**Не делите на 100 вслепую.** У XTR, JPY, KRW и VND нет дробной части: 150 XTR — это ровно 150. Используйте `minor_to_units`.

**Не рассчитывайте на единственный вебхук.** Провайдеры повторяют уведомления при любой неопределённости. Ядро отсекает дубликаты по `external_event_id` и по статусу платежа, но верните честный идентификатор события — иначе защита не сработает.

**Не продлевайте подписку сами.** Ваша задача — вернуть `WebhookOutcome`. Продление, сверку суммы и защиту от повторов делает ядро в одной транзакции.

## Что ядро делает за вас

- Создаёт запись платежа **до** обращения к провайдеру — уведомление не потеряется, даже если придёт мгновенно.
- Блокирует строку платежа при обработке: два одновременных вебхука не продлят подписку дважды.
- Сверяет пришедшую сумму с ожидаемой и не продлевает при недоплате.
- Продлевает от большей из дат — истёкшая подписка считается от сегодня, а не от даты в прошлом.
- Возвращает доступ клиентам со статусом «истёк» или «лимит».
- Пишет все входящие уведомления в `payment_webhooks`, включая отклонённые по подписи, — по этому журналу разбирают инциденты.

## Тестирование

Проверьте хотя бы это:

```bash
cargo test -p sn-payments
```

- подпись с верным ключом принимается;
- подпись с неверным ключом отклоняется;
- отсутствие ключа не приводит к «принято»;
- суммы в валютах без копеек не делятся на 100.
